# claude-md-doctor

CLAUDE.md 시스템을 진단(Step 1)하고, 그 결과를 바탕으로 개선 실행 계획(Step 2)을
같은 호출 안에서 바로 이어서 산출한다. 두 단계 모두 **읽기 전용** — 실제 파일
수정은 이 스킬의 범위 밖이며, 사용자가 계획을 검토한 뒤 별도로 요청해야 한다.

## 파이프라인 개요

```
[Step 1] 진단
  ├─ 대상 파일 수집 (Global/Local CLAUDE.md, .claude/rules/, 하위 계층, 실제 폴더 구조)
  ├─ 4개 역할 기준 평가 (프로젝트 지도 / 규칙서 / 능력의 경계선 / 시행착오 일지)
  ├─ 구조 품질 점검 (라인 수 / Global-Local 분리 / rules 활용 / 계층 구조 / 중복)
  └─ 항목별 [충족 / 부분 충족 / 미충족] 판정표 출력

[Step 2] 개선 실행 계획 (Step 1 직후 자동 이어서 실행, 사용자 확인 불필요)
  ├─ [충족] 항목은 건드리지 않음
  ├─ [부분 충족] / [미충족] 항목만 대상으로 변경안 도출
  └─ 우선순위([높음/중간/낮음])가 매겨진 실행 계획 출력 (코드 미수정)
```

## Step 1: CLAUDE.md 시스템 진단

### 대상 파일 수집

- `~/.claude/CLAUDE.md` — Global (존재하면)
- `<repo-root>/CLAUDE.md` — Local
- `<repo-root>/**/CLAUDE.md` — 하위 디렉토리 계층 (존재하면)
- `.claude/rules/*.md` — 존재하면, 각 파일의 `paths` frontmatter 필드 유무 확인
- 실제 폴더 구조 스냅샷 — `git ls-files` 또는 최상위 2~3 depth 탐색으로, CLAUDE.md에
  기술된 구조와 대조할 기준선을 만든다

### 평가 기준

아래 4가지 역할 기준으로 각각 평가한다:

**1. 프로젝트 지도 (Project Map)**
- 현재 프로젝트의 실제 폴더 구조와 CLAUDE.md에 기술된 구조가 일치하는가?
- 주요 디렉토리별 역할이 명시되어 있는가?
- 클로드가 파일 탐색 없이 원하는 코드 위치를 바로 찾을 수 있는 수준인가?

**2. 규칙서 (Rules & Preferences)**
- 코딩 스타일, 언어 선호, 라이브러리 선호가 명시되어 있는가?
- 커뮤니케이션 스타일(응답 포맷, 설명 깊이, 언어)이 정의되어 있는가?
- 프로젝트의 목표나 맥락이 포함되어 있는가?
- 더 이상 유효하지 않은 규칙이 남아있는가?

**3. 능력의 경계선 (Capability Boundaries)**
- 이 프로젝트에서 사용 가능한 외부 API, DB, 자동화 스크립트가 명시되어 있는가?
- API 문서가 프로젝트 내부에 존재하는 경우, 참조 경로가 안내되어 있는가?
- 클로드가 "이 기능을 수행할 수 없습니다"라고 잘못 판단할 수 있는 영역이 있는가?

**4. 시행착오 일지 (Lessons Learned)**
- 이전에 실패한 접근 방식이 기록되어 있는가?
- 특정 라이브러리/버전 호환성 이슈가 문서화되어 있는가?
- 반복되는 실수를 방지하는 가드레일이 존재하는가?

추가로 아래 구조적 품질도 점검한다:

**구조 점검**
- CLAUDE.md 총 라인 수 (200줄 이내 권장)
- Global(`~/.claude/CLAUDE.md`)과 Local(프로젝트 `CLAUDE.md`) 분리 여부
- `.claude/rules/` 디렉토리 활용 여부
- 하위 폴더별 CLAUDE.md 계층 구조 활용 여부
- 불필요하게 중복된 내용 존재 여부

### 출력 형식 (Step 1)

각 항목(4개 역할 + 구조 점검 5개 = 총 9개 이상)에 대해:

- **판정**: `[충족 / 부분 충족 / 미충족]`
- **근거**: 실제 파일 경로 + 해당 라인(가능하면 라인 번호) 인용
- 미충족/부분 충족이면 한 줄 개선 방향도 함께 제시 (Step 2 입력으로 재사용)

## Step 2: 개선 실행 계획

Step 1 직후, **사용자 확인 없이 바로 이어서** 실행한다. Step 1에서 `[부분 충족]`
또는 `[미충족]`으로 판정된 항목만 대상으로 하며, `[충족]` 항목은 다루지 않는다.

### 반드시 지킬 원칙

1. **기존에 잘 작동하는 부분(`[충족]` 판정 항목)은 건드리지 않는다.**
2. 각 변경 사항은 아래 포맷으로 정리한다:
   - **변경 위치**: (파일 경로)
   - **변경 유형**: `[추가 / 수정 / 삭제 / 분리]`
   - **현재 상태**: (현재 내용 요약)
   - **개선 후**: (변경될 내용 요약)
   - **이유**: (왜 이 변경이 필요한지 — Step 1의 판정 근거와 연결)
3. 아래 Anthropic 권장 사항을 반영한다:
   - CLAUDE.md는 200줄 이내로 유지, 영어로 작성
   - 규칙이 많으면 `.claude/rules/` 디렉토리로 분리
   - 각 규칙 파일에 `paths` 필드를 활용해 특정 폴더에서만 적용되도록 스코핑
   - 하위 폴더에 별도 CLAUDE.md가 필요한 경우 계층 구조 제안
   - 단, 프로젝트가 이중언어(예: 한국어 본문 + 영어 섹션 태그) 컨벤션을 **의도적으로
     명시**하고 있다면 이를 무시하고 전면 영어화를 강제하지 말 것 — 그 충돌 사실을
     명시하고 우선순위 판단은 사용자에게 맡긴다.
4. 변경 우선순위를 `[높음 / 중간 / 낮음]`으로 매긴다.

### 출력 형식 (Step 2)

우선순위(`높음` → `중간` → `낮음`) 순으로 정렬된 변경 목록. 각 항목은 위 포맷을
그대로 따른다.

### 제약

- **실행 계획만 세운다. 코드/문서를 실제로 수정하지 않는다.**
- 계획 산출 이후 실제 반영은 사용자가 별도로 요청했을 때만 진행한다.
